# Магазин цифровых товаров

Тестовое задание: витрина, покупка цифрового товара и выдача ключа после оплаты.
Основная часть работы не в вёрстке, а в том, чтобы ключ ушёл покупателю **ровно
один раз** — даже когда платёжка шлёт полсотни одинаковых вебхуков, поставщик
отваливается по таймауту, а покупатель дважды кликает «Купить».

Демо: https://ggsell.prettysites.ru, админка — `/admin/`.

## Стек

PHP 8.3, MySQL 8, фронт — HTML/CSS/JS без фреймворков. Composer и сторонних
библиотек нет: задача маленькая, а всё, что нужно, есть в стандартной поставке.

Макет нарисован под 1200, но раскладка резиновая: контейнер тянется до 1200,
ниже вступают брейкпоинты — ряд иконок и вкладки прокручиваются, блок пополнения
и меню каталога складываются в колонку, карточек в ряду столько, сколько влезает.
На телефоне баннер листается свайпом, стрелок там нет.

## Запуск

Нужна пустая база MySQL и пользователь к ней, остальное сделает сид:

```
cp app/config.local.php.example app/config.local.php   # доступы к базе и токен админки
php tools/seed.php --reset                             # схема + данные из ТЗ
```

Корень сайта — корень репозитория. `app/` и `storage/` закрыты `.htaccess`,
плюс в `app/bootstrap.php` стоит вторая проверка: без константы `APP` файл
отвечает 404. Всё, что приходит в `/api/`, разбирает один `api/index.php`.

`--reset` чистит заказы, события и занятые коды, но каталог и склад оставляет —
удобно перед прогоном проверок.

## Как проходит покупка

1. Клик по «Купить» — `POST /api/orders`. С клиента приходят только `sku`,
   промокод и токен от двойного клика; сумму и скидку считает сервер.
2. Браузер уходит на `order.html?id=ord_00001`.
3. Кнопка «Оплатить» дёргает `POST /api/orders/{id}/pay` — эмуляция эквайринга.
   Реальных денег нет, ручка просто шлёт магазину такой же вебхук, какой прислала
   бы платёжная система.
4. Вебхук переводит заказ в `paid` и запускает выдачу.
5. Страница переспрашивает статус, пока заказ в `paid`/`delivering`, и показывает
   ключ, как только он привязан.

Статусы заказа: `created → paid → delivering → delivered`, плюс три тупиковых
или восстановимых — `payment_failed`, `out_of_stock`, `delivery_failed`.

## API

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/products` | каталог |
| POST | `/api/orders` | создать заказ: `{sku, client_token, promo_code}` |
| GET | `/api/orders/{id}` | статус заказа, ключ отдаётся только в `delivered` |
| POST | `/api/orders/{id}/pay` | эмуляция оплаты; в `result` — `success` или `fail` |
| POST | `/api/webhook/payment` | вебхук платёжки: `{event_id, order_id, status, amount}` |
| POST | `/api/promo/quote` | предпросмотр скидки: `{code, sku}` |
| POST | `/api/supplier/{a\|b}/issue` | заглушка поставщика: `{request_id, sku, order_id}` |

Админские ручки закрыты заголовком `X-Admin-Token`:

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/admin/orders?status=stuck` | заказы; `stuck` — оплаченные без ключа |
| POST | `/api/admin/orders/{id}/redeliver` | повторная выдача (идемпотентна) |
| GET | `/api/admin/stock` | остатки поставщиков |
| POST | `/api/admin/stock/refill` | пополнить склад: `{supplier, count}` |
| POST | `/api/admin/webhooks/replay` | применить события, пришедшие раньше заказов |

## Где именно обеспечена однократная выдача

Ни одна проверка не сделана «сначала SELECT, потом решаем»: между чтением и
записью успевает влезть соседний запрос. Решение везде принимает база.

- **Повторная доставка вебхука.** `UNIQUE(event_id)` в `webhook_events`. Вставка
  дубля не проходит — обработчик отвечает `duplicate_ignored` и выходит.
- **Пятьдесят вебхуков разом.** `UPDATE orders SET status='paid' WHERE id=? AND
  status='created'`. Строку меняет ровно один запрос, у остальных `rowCount = 0`,
  и до поставщика они не доходят.
- **Таймаут поставщика.** `request_id` детерминированный — номер заказа плюс буква
  поставщика. Таймаут не означает отказ: код мог быть выдан, а ответ не дойти,
  поэтому мы не просим новый код, а переспрашиваем тем же `request_id`. Заглушка
  по контракту возвращает тот же код — за это отвечает `UNIQUE(taken_by)`
  в `supplier_stock`.
- **Привязка кода к заказу.** `UPDATE ... SET delivered_code = ? WHERE id = ? AND
  delivered_code IS NULL` — последний рубеж: даже если сюда придут два кода,
  запишется первый.
- **Двойной клик по «Купить».** `UNIQUE(client_token)` в `orders`: второй запрос
  упирается в индекс и получает заказ, созданный первым.
- **Лимит промокода.** `UPDATE promo_codes SET used = used + 1 WHERE code = ? AND
  used < max_uses` внутри транзакции вместе с заказом. Не сработало — исключение
  откатывает и запись об использовании, и сам заказ.

## Сбои и восстановление

Выдача не бросает исключений «наверх»: заказ, который оплачен, но остался без
ключа, переходит в восстановимый статус, а не в ошибку.

- Кончились коды у поставщика A — резервный B тут не поможет, заказ уходит
  в `out_of_stock` и ждёт пополнения склада.
- Оба поставщика не ответили — `delivery_failed`.
- В обоих случаях админка показывает заказ в списке «оплачен, но не выдан»,
  а кнопка «Выдать ключ» доводит его до конца. Повторное нажатие безопасно:
  если код уже привязан, сервер вернёт его же.
- Вебхук пришёл раньше, чем создан заказ — событие сохраняется и применяется
  в момент создания заказа. Отвечаем при этом `200`, иначе платёжка будет
  долбиться повторами.

## Проверка гонок

```
php tools/seed.php --reset && php tools/race_test.php
```

Запускать на сервере, рядом с приложением. Параллельные запросы идут по HTTP
через `curl_multi` — это настоящая конкуренция между воркерами php-fpm, а не
эмуляция внутри одного процесса. Результат сверяется прямо в базе: важно не то,
что ответил API, а то, что реально легло в таблицы.

Шесть сценариев, 19 проверок:

1. 50 параллельных вебхуков «оплачено» по одному заказу.
2. Повтор вебхука с тем же `event_id`.
3. Вебхук раньше создания заказа.
4. Пустой склад: восстановимый статус, пополнение, пять повторных выдач подряд.
5. Промокод с лимитом 3 под пятнадцатью параллельными запросами.
6. Двойной клик по «Купить»: десять запросов с одним токеном.

Адрес меняется флагом: `php tools/race_test.php --base=https://example.com`.

## Заглушки поставщиков

Поставщики A и B — наши же ручки, но ходим к ним по HTTP, как к чужому сервису:
иначе таймауты и повторы нечем воспроизводить. Долю сбоев можно задрать прямо
в запросе, не трогая конфиг:

```
POST /api/supplier/a/issue?fail_rate=1
POST /api/supplier/a/issue?timeout_rate=1&hang_seconds=8
```

Заглушка зависает **после** того, как код уже выдан, — это и есть интересный
случай: ответ не дошёл, а код списан.

## Что упрощено сознательно

- Выдача идёт в том же запросе, что и вебхук, — после раннего `200 OK`
  (`Http::respondEarly`). В проде здесь была бы очередь; для задания достаточно
  php-fpm, который доводит запрос после ответа клиенту.
- Оплата эмулируется ручкой `/pay`: настоящего эквайринга в задании нет.
- Админка закрыта одним токеном, без пользователей и ролей — по ТЗ авторизация
  не требуется.
- Переключатель валют меняет только символ: пересчёта по курсу в ТЗ нет.
- Тёмной темы нет — по ТЗ она не нужна.
